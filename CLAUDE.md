# CLAUDE.md

JetPack for WPF: the JetPack theme from Microsoft's Silverlight 4 Application Themes, rebuilt as a
WPF controls library for .NET 8+ in the style of MahApps.Metro. Repo: github.com/Montago/JetPackTheme
(default branch `master`).

## Rules

- **Everything in the repo is English**: code, comments, XAML strings, demo text, sample data,
  READMEs, commit messages. The user chats in Danish; replies can be Danish.
- Keep the original JetPack look: values come from the Silverlight files (`Brushes.xaml`,
  `CoreStyles.xaml`, `SDKStyles.xaml`, `ToolkitStyles.xaml`). Originals live in
  `D:\Dropbox\SL4Themes-RawAssets\JetPack`, `D:\Dropbox\SL4Themes-templates` and the old demo in
  `D:\Dropbox\Projects\Jetpack.Demo`.
- Everything in the repo is MIT, including `Assets/Texture.png`, which `tools/generate_backgrounds.py`
  draws from scratch (the vignette is drawn in code by `Controls/Vignette.cs`). Never copy Microsoft's image or XAML files in;
  take values (colours, sizes) from them and draw or write the rest yourself.
- The check mark (`JetPack.Geometry.Check`, and the mask in `jetpack.css`) is the original theme's
  path data, kept on purpose by the user for check boxes and checkable menu items; do not redraw it.
- The licence exception (approved by the user): the icons are Material Design Icons (Apache 2.0), kept
  unchanged in `icons/mdi/` with their licence in `icons/` and a note in `NOTICE.md`; the package
  licence is `MIT AND Apache-2.0`. Add icons only from that set.
- Never commit screen captures that show the user's desktop.
- When a control, property or style key changes, update the matching page in `docs/` in the same
  commit and regenerate `docs/resource-keys.md`. The same goes for the web theme: a tag helper,
  attribute, class or `jetpack.js` behaviour that changes gets its page in `docs/web/` updated.

## Layout

```

  Styles/Brushes.xaml, Fonts.xaml, Effects.xaml, Accents/{Green,Orange,Blue}.xaml
  Styles/Controls.*.xaml    one file per control group
  Themes/Generic.xaml       merges JetPack.xaml (needed: implicit styles don't reach subclasses
                            such as MainWindow : JetPackWindow)

  Helpers/                  ControlHelper / TextBoxHelper attached properties, converters
  Theming/                  ThemeManager, AccentGenerator
src/JetPack.Wpf.Demo/       demo app; pages in Views/
src/JetPack.Web/            web theme (Razor class library, net8.0; NuGet package JetPack.Web):
                            wwwroot/css/jetpack.src.css imports jetpack.tokens.css (generated) and
                            css/controls/*.css (one per Controls.*.xaml); jetpack.css is that bundled
                            into one file by tools/bundle_web_css.py (sites link it; never edit it);
                            js/jetpack.js (all behaviour, no dependencies); img/texture.png and icons.svg
                            (generated); TagHelpers/ (<jp-*> for every demo control, WPF property names)
src/JetPack.Web.Demo/       the WPF demo as a web page: Views/Demo/Pages/<UserControl>.cshtml per tab,

                            Views/Demo/Gallery.cshtml (/Demo/Gallery) is the web GalleryPage
samples/                    sample apps: JetPack.Wpf.Samples.Admin (HamburgerMenu) and .Portal
                            (navigation bar); presentation only, fixed data in SampleData.cs, one
                            UserControl per page in Views/, Shared/WindowSnapshot.cs for --snapshot;
                            JetPack.Web.Samples.Mvc is the admin sample as an ASP.NET Core MVC site
                            (links the admin SampleData.cs, Tailwind browser build for layout)
docs/                       component documentation (Markdown); keep it in step with the code.
                            docs/*.md is the home page and JetPack for WPF; docs/web/*.md is JetPack for
                            the web (parent page docs/web.md), with the same page names as the WPF pages
docs/resource-keys.md       generated: run `python tools/generate_resource_keys.py` after changing Styles/
docs/_data/nav_headings.yml generated by tools/generate_nav_headings.py (via update_docs.py): the page
                            headings that docs/assets/js/nav-headings.js adds to the docs menu
tools/generate_backgrounds.py   draws Assets/Texture.png (numpy + Pillow)
icons/icons.json            the icon set: MDI names (as in MahApps' IconBrowser); SVGs in icons/mdi/
tools/generate_icons.py     icons.json -> JetPackIconKind.g.cs (WPF and web) and JetPack.Web's img/icons.svg;
                            --fetch downloads SVGs that are missing (pinned @mdi/svg version)
tools/generate_web_tokens.py    writes JetPack.Web's jetpack.tokens.css from Styles/*.xaml and copies
                                the texture; run it after changing brushes, fonts, effects or accents
tools/bundle_web_css.py     bundles jetpack.src.css and its imports into JetPack.Web's jetpack.css; run it
                            after editing the web CSS or the tokens (CI fails when it is out of date)
tools/update_docs.py        rebuilds all screenshots + resource keys and runs the docs checks
.claude/skills/update-docs/ the /update-docs skill: runs the script, reviews pictures, fixes the text
design/jetpack-preview.src.html   approved HTML/CSS draft (texture as __TEX__ placeholder)
design/jetpack-preview.html       same file with the texture inlined as base64
docs/screenshots/           README images, produced by --snapshot
docs/screenshots/controls/  one picture per control for the docs pages (from Views/GalleryPage.xaml)
```

Resource keys follow MahApps with a `JetPack.` prefix (`JetPack.Brushes.Accent`,
`JetPack.Styles.Button.Accent`, ...). ThemeManager swaps accents by adding dictionaries at the end of
`Application.Resources`, so brushes must be referenced with `DynamicResource`.

## Build and verify

```bash
dotnet build JetPack.Wpf.sln
src/JetPack.Wpf.Demo/bin/Debug/net8.0-windows/JetPack.Wpf.Demo.exe --snapshot <folder>
```

- `--snapshot` renders every demo page (plus orange/blue accent, light title bar, dialog, flyout) to
  PNG via RenderTargetBitmap and exits; it forces en-US so screenshots stay English. Look at the
  PNGs after every visual change, then copy the relevant ones to `docs/screenshots`.
- It also renders each sample of `Views/GalleryPage.xaml` (a `Demo.Sample` whose `Tag` is the file
  name) to `<folder>/controls`; copy those to `docs/screenshots/controls`. Elements marked
  `d:Demo.Open="True"` get their drop-down, menu, tool tip or validation call-out opened, and
  `GallerySnapshot` draws the popup where its placement would put it. A new control or variant gets a
  sample there and a picture under its heading in `docs/`.
- `docs/screenshots/mica.png` is an on-screen capture (Mica cannot be rendered with
  RenderTargetBitmap), approved by the user although its tint comes from their wallpaper. The
  scripts do not make it; keep it unless the user asks for a new one.
- The sample apps also take `--snapshot <folder>` (one PNG per page, named `admin-*` / `portal-*`);
  copy them to `docs/screenshots/samples` when the apps or the look change.
- RenderTargetBitmap returns blank (fully transparent) images while the PC's screen is off or the
  session is locked; connect (e.g. RDP) before running `--snapshot`.
- The user often runs the demo from Visual Studio, which locks `bin\...\JetPack.Wpf.dll`. Do not kill
  it; build to another folder instead: `dotnet build src/JetPack.Wpf.Demo -o <scratch>/out`.
- RenderTargetBitmap does not show what DWM draws (rounded window corners, system frame) or popups
  (drop-downs, menus, tooltips). For those, start the exe on screen, drive it with UI Automation from
  PowerShell (SelectionItemPattern on named elements) and capture with `Graphics.CopyFromScreen`
  after `SetProcessDPIAware`.
- After editing XAML, check that every `{StaticResource X}` is defined earlier in the same file:
  `python tools/update_docs.py --check` does this along with the docs checks.
- **Updating the docs:** run `/update-docs` (or `python tools/update_docs.py` for just the mechanical
  part) before a release and after larger changes. It renders the demo pages, the gallery and the
  sample apps with endless animations frozen, so pictures only change when the look does.
  Exceptions: the calendars mark today, so `calendar`, `datepicker`, `sdk`, `window`, `window-light`,
  `dialog` and `flyout` change every day, and on the web `web/sdk`, `web/controls/calendar` and
  `web/controls/datepicker`; revert them when only the date moved. PNGs are also
  re-encoded on every run, so compare pixels (RGB and alpha; `Image.getbbox()` on an RGBA
  difference looks at alpha only) rather than bytes.

## NuGet package and releases

- Two packages, each with its own version: `JetPack.Wpf` and `JetPack.Web`. Package metadata lives
  in each `.csproj`; the project's `PACKAGE.md` becomes the package README on nuget.org (absolute
  image URLs only), `src/JetPack.Wpf/icon.png` the icon of both. License: `MIT AND Apache-2.0`.
- Before tagging a release, run `/update-docs` so screenshots and docs match the code.
- `.github/workflows/release.yml` publishes on a `v*.*.*` tag: always to GitHub Packages (workflow
  token, `--no-symbols` because that feed rejects snupkg), and to nuget.org with Trusted Publishing
  (`NuGet/login@v1`, OIDC, policy for `release.yml`) when the `NUGET_USER` secret exists. The tag
  picks the package and its version: `v1.2.3` is JetPack.Wpf (`git tag -a v1.2.3 -m "JetPack.Wpf 1.2.3"`,
  then `git push origin v1.2.3`), `web-v1.2.3` is JetPack.Web (not marked as the latest GitHub
  release). It can be re-run for an existing tag: published packages are skipped and the release
  assets replaced.
  Never handle API keys or secrets yourself; the user sets them.
- `.github/workflows/ci.yml` builds every push and pull request, checks that `jetpack.css` matches
  its sources, and uploads both packages as an artifact.
- A package's static web assets (`_content/...`) return 404 when a plain `dotnet build` output
  runs as Production; test a consumer app with `dotnet publish` (or as Development).
- `dotnet nuget push artifacts/*.nupkg` does not expand the glob on the Windows runner; loop in bash.
- `gh api` here lacks `read:packages`; check packages on
  https://github.com/Montago/JetPackTheme/pkgs/nuget/JetPack.Wpf instead.
- To test the package without touching the global NuGet cache: pack with `-p:Version=0.0.1-localtest`
  into a scratch feed, then build a small consumer app with its own `nuget.config` and
  `--packages <scratch>/pkgs`.

## Docs site gotchas

- Just the Docs compresses every page onto one line, so inline `<script>` in `docs/_includes/` must not
  use `//` comments (they hide the rest of the script); use `/* */`.
- Browsers keep the old HTML for a while after a Pages build; add a query string (`?v=<commit>`) when
  checking a change on the live site.

## WPF gotchas found in this project

- **StaticResource / BasedOn across files fails** at runtime. Each `Controls.*.xaml` is loaded on its
  own, so cross-file references must be `DynamicResource`, and `BasedOn` styles must live in the same
  file as their base (that is why the ToolBar child style keys sit in Buttons/Toggles/Text/Lists).
- **Built-in theme styles still apply under implicit styles.** Aero2 sets e.g. `Foreground` on
  TabItem, TreeViewItem and Button, which overrides inheritance (black text on dark backgrounds).
  Fix with `OverridesDefaultStyle=True` on styles that supply a full template (done for TabItem,
  TreeViewItem, window caption/command buttons).
- **TabItem properties leak into the page.** Page content inherits FontSize/FontWeight/Foreground
  from the TabItem, and TabControl aligns the content by the TabItem's `HorizontalContentAlignment`.
  Keep header fonts/colours on the header ContentPresenter (`ControlHelper.HeaderForeground`) and
  set `HorizontalContentAlignment=Stretch` on tab items.
- **Text rendering:** the window uses `TextFormattingMode=Display` (crisp small text); headings and
  tab headers use `Ideal`, otherwise large text looks jagged.
- **Culture set inside async `OnStartup` is reset at the first await.** Set thread culture in the
  `App` constructor. WPF also formats bindings as en-US unless `FrameworkElement.LanguageProperty`
  is overridden.
- **Rounded corners** come from `DwmSetWindowAttribute` (corner preference 33, border colour 34) on
  Windows 11; on Windows 10 they stay square. The template drops its own border when
  `HasSystemRoundedCorners` is true.
- `Checked` handlers on RadioButtons with `IsChecked="True"` fire during `InitializeComponent`,
  before later attributes such as `Tag` are set; guard with `IsLoaded`.
- **TextBox and PasswordBox apply `Padding` to their text themselves.** Do not also put `Padding` on
  the element around `PART_ContentHost`, or the text gets it twice and no longer lines up with the
  watermark. Give the watermark `Margin="{TemplateBinding Padding}"` plus the 2px text inset instead.
- **Submenu items inherit Foreground from their header MenuItem through the logical tree**, not from
  the popup they sit in. Header templates therefore set `TextElement.Foreground` on the header
  presenter, never `Foreground` on the MenuItem itself.
- A Binding inside a ControlTemplate cannot be removed with `BindingOperations.ClearBinding` (that
  only clears local values); setting the property routes through a two-way template binding. Put a
  local binding on top instead (see `GallerySnapshot.ForceOpen`).
- **Attached properties in binding paths need `jp:` (`urn:jetpack-wpf`), not `c:`/`h:`.** A path such
  as `{Binding (h:ControlHelper.X)}` is resolved at run time, and a `clr-namespace` without
  `assembly=` then points at the app's assembly, so the binding silently finds nothing. Adding
  `assembly=JetPack.Wpf` breaks the build instead (the compiler cannot load its own assembly).
  Setters, `TemplateBinding` and `TargetType` are resolved at compile time and are fine with `c:`/`h:`.
- **An implicit `DataGridColumnHeader` style wins over `DataGrid.ColumnHeaderStyle`**, and
  `DataGridColumnHeader.Column` does not notify. JetPackGrid puts its header style in
  `Style.Resources` and binds through `JetPackGrid.HeaderColumn`.
- Effects (DropShadowEffect) on text turn off ClearType; put shadows on a separate background
  Border rather than on content, except for the deliberate text emboss/glow.

## Known limitations / ideas

- Cells of `DataGrid`/`JetPackGrid` keep WPF's own check box (`DataGridCheckBoxColumn`) and edit
  fields (`DataGridTextColumn`, `DataGridComboBoxColumn`): chosen by the user, not a gap. Do not add
  JetPack element or editing styles for these columns; `docs/lists.md` shows how an app opts in.
- TabControl supports top tabs only; DatePicker watermark text comes from WPF and is English.
- Popups (combo drop-downs, menus, tooltips, DatePicker) are checked in the gallery snapshots, but
  not yet driven interactively with the mouse.
- The web demo mirrors the WPF demo tab for tab (JetPackGrid left out on purpose); when a WPF
  demo page changes, change its `.cshtml` twin. Web class names follow the WPF names (`ComboBox` ->
  `.jp-combo-box`, `JetPack.Styles.Button.Accent` -> `.jp-button--accent`) and tag helper attributes
  the WPF properties (`IsEnabled` -> `is-enabled`); keep that rule when adding controls. Load
  `jetpack.css` before Tailwind.
- Web CSS pitfalls: selectors for TabControl.Strip/Navigation must use child combinators (pages sit
  inside a strip TabControl); a relative `url()` in a CSS variable resolves against the file that
  uses it, hence `@property --jp-window-background { syntax: "<url>" }` in the tokens; submenus are
  popovers nested in their parent menu (opening an unrelated popover closes the others).
- Pictures of the web demo (`docs/screenshots/web/*.png`) and the web sample
  (`docs/screenshots/samples/web-*.png`) come from `python tools/web_snapshots.py`: it builds both
  sites to a scratch folder, runs them, and takes 1280 × 900 pictures with headless Edge;
  `update_docs.py` runs it too. Compare them with the WPF pictures of the same tab after a change.
- The web gallery (`Views/Demo/Gallery.cshtml`) has one `.gallery-sample[data-shot=<name>]` per
  control, named as in `GalleryPage.xaml`. `/Demo/Gallery?shot=<name>` shows that sample on magenta
  and opens what is marked `data-demo-open` (`wwwroot/js/gallery.js`); `web_snapshots.py` cuts it out
  to `docs/screenshots/web/controls/<name>.png`. A new web control or variant gets a sample there
  and a picture under its heading in `docs/web/`. Compare each with `docs/screenshots/controls/` (WPF).
- The demo pictures are taken with `?snapshot`, which freezes endless animations
  (`html[data-snapshot]` in `demo.css`); `web_snapshots.py` ignores Edge's one-level raster noise.
